## 浏览器中的事件循环

浏览器中的事件循环是单线程的，但是浏览器是多进程的。

### 浏览器进程

浏览器进程负责：
- 页面显示
- 用户交互
- 子进程管理

### 网络进程

网络进程负责：
- 网络资源加载
- 网络请求
## 进程与线程

进程是资源分配的最小单位

线程是CPU调度的最小单位

### 进程

程序运行需要有自己专属的内存空间，可以把这块内存空间理解为进程。
每一个应用至少有一个进程，进程之间相互独立。
比如浏览器打开一个页面就是一个进程

### 线程

具体做事的。比如浏览器的一个页面会分配多个线程，比如
- 渲染主线程：自上而下渲染页面
- HTTP网络请求线程：加载资源文件以及数据
- 定时器监听线程：监听定时器是否到时间
- DOM事件监听线程：监听DOM事件触发
- ......

## 进程和线程的关系

进程包含一个或多个线程，进程开启后会创建一个线程来运行代码，这个线程成为主线程。

主线程负责执行程序中的代码，其他线程负责执行一些特定的任务，如：渲染、IO操作等。

## 浏览器中的进程

> 可以在浏览器的任务管理器中查看当前所有的进程

浏览器是多进程的，包括但不限于以下进程：

1. 浏览器主进程
主要负责界面展示、用户交互、子进程管理等。浏览器内部会启动多个线程处理不同任务。
2. 网络进程
负责加载网络资源。网络进程内部会启动多个线程来处理不同的网络任务。
3. GUI渲染进程（一个标签页就是一个渲染进程）
渲染进程启动后，会开启一个 ***渲染主线程*** ，主线程负责执行 HTML、CSS、JS 代码，解析 DOM 结构、计算样式、布局、绘制页面等。  
默认情况下，浏览器会为每一个标签页开启一个新的渲染进程，以保证不同标签页之前不会互相影响。
4. GPU进程
其实， GPU 的使用初衷是为了实现 3D CSS 的效果，只是随后网页、Chrome 的 UI 界面都选择采用 GPU 来绘制，这使得 GPU 成为浏览器普遍的需求。最后，Chrome 在其多进程架构上也引入了 GPU 进程。
5. 插件进程
主要是负责插件的运行，因插件易崩溃，所以需要通过插件进程来隔离，以保证插件进程崩溃不会对浏览器和页面造成影响。
所以，打开一个网页，最少需要四个进程：1 个网络进程、1 个浏览器进程、1 个 GPU 进程以及 1 个渲染进程。如果打开的页面有运行插件的话，还需要再加上 1 个插件进程。

## 浏览器GUI渲染进程

GUI渲染进程总共有以下五中线程：
- GUI渲染主线程  
- JS引擎线程  
- 事件触发线程  
- 定时触发器线程  
- 异步http请求线程

### GUI渲染主线程

GUI渲染主线程负责渲染页面，解析HTML、CSS， 计算样式，图层，每秒把页面绘制60次，执行全局JS,执行事件处理函数，执行计时器函数等。
> 如果分配多个渲染主线程来处理这些事件，会导致冲突。比如处理同一个点击事件，可能导致另外的东西不存在

由于主线程需要处理的事情很多，所以通过 ***排队*** 来处理

![事件队列](/images/notes/js/eventloop.png)  

1. 在最开始的时候渲染主线程会进入一个无限循环
2. 每一次会检查消息队列中是否有任务，如果有任务，取出第一个任务执行，执行完成后进入下一次循环，没有任务后会进入休眠状态
3. 其他的线程可以随时向消息队列中添加任务到消息队列的末尾，如果主线程是休眠状态会唤醒主线程继续循环执行任务  
**整个循环就被称作 事件循环（消息循环）**


#### 异步

**单线程是异步产生的原因。事件队列是异步的解决方式**

在代码执行过程中，会碰到一些无法立即执行的任务，比如：
- 计时器完成后需要执行的任务 -- **setTimeout、setInterval**
- 网络通信完成后需要执行的任务 -- **Ajax、Fetch**
- 用户触发的事件完成需要执行的任务 -- **addEventListener**

如果让渲染主线程等待这些任务的时机到达，就会导致主线程长期处于 *阻塞*状态，导致浏览器*卡死*，  
**而主线程承担着极其重要的作用，不管怎么样都不能阻塞**  
因此，必须采用异步的方式，将这些任务从主线程中移除，放到一个单独的地方，等时机到达时，再将任务添加到消息队列中，等待主线程执行。

> **如何理解 JS 的异步**  
JS 是一门单线程的语言，这是因为他运行在浏览器的渲染主线程中，而渲染主线程只有一个，并且承担着很多的工作，如渲染页面、执行 JS 都在其中运行。  
如果使用同步的方式，可能导致主线程产生阻塞，从而导致消息队列中很多其他任务无法得到执行。  
这样一来，一方面使得主线程白白消耗时间，另一方面导致页面无法及时更新，给用户造成卡死现象。  
所以浏览器采用异步的方式来避免。具体做法是当某些任务发生时，比如计时器、网络、事件监听，主线程将任务交给其他线程去处理，自身立即结束任务的执行，转而执行后续代码。当其他线程完成时，将事先传递的回调函数包装成任务，加入到消息队列的末尾，等待主线程调度执行。  
在这种异步模式下，浏览器不阻塞，最大限度的保障单线程的流畅运行。

#### 优先级
任务没有优先级，在纤细队列中先进先出  
但**消息队列有优先级**   
根据 W3C 的最新解释：  
- 每个任务都有一个任务类型，同一个类型的任务必须在一个队列，不同类型的任务可以分数不同的队列。  
  在一次时间循环中，浏览器可以根据实际情况再不同的队列中取出任务执行。
- 浏览器必须准备好一个微队列，微队列中的任务优先所有其他任务执行。  
  [任务队列优先级](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint)

> 随着浏览器的复杂度几句提升， W3C 不在使用宏队列的说法。

目前 Chrome 的实现中，至少包含了以下队列：
- 延时队列：用于存放计时器到达后的毁掉任务，优先级[中]， `setTimeout, setInterval`
- 交互队列：用户存放用户操作后产生的时间处理任务，优先级[高], `addEventListener`
- 微队列：用户存放需要最快执行的任务，优先级[最高]， 包括`Promise.resolve().then(), MutationObserver, requestAnimationFrame等`

> **阐述 JS 的事件循环**   
事件循环又称消息循环，是浏览器渲染主线程的工作方式。  
在 Chrome 的源码中，它开启一个不会结束的 for 循环，每次循环从消息队列中取出第一个任务执行，而其他线程只要在核实的时候将任务加入到队列默认即可。  
现在是将任务分成多种不同的类型，比如`延时任务，交互任务，微任务`,每个任务都有不同的类型，同类型的任务必须在同一个队列，不同类型的任务可以分属不同的队列。不同任务队列有不同的优先级。在一次事件循环中，有浏览器自行决定取哪个队列的任务，但浏览器碧玺有一个微队列，且具有醉倒的优先级，必须优先调度执行。

> **JS中的计时器能做到精确计时吗**  
> 不行，因为
> 1. 计算机硬件没有原子钟，无法做到精确计时。
> 2. 操作系统的计时函数本身就有少量偏差，由于 JS 的计数器最终调用的是操作系统的函数，也就携带了这种偏差。
> 3. 按照 W3C 的标准，浏览器实现计时器时，如果时间少于 4ms, 会增加到 4ms。 如果嵌套层级超过 5 层，会带有 4ms 的最少时间。
> 4. 受到事件循环的影响，计时器的回调函数只能在主线程空闲时运行，又会带来偏差
